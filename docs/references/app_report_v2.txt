四合一效率成长 APP
文档审核与增强版落地手册
基于 DayMark、OffScreen、番茄ToDo、HabitDone 的功能融合、UI 架构与低成本开发修正版
适用对象：想把四款效率/习惯/专注/数字健康 APP 做成一个新产品的个人开发者或小团队
建议定位：先做“个人成长与专注管理”的高完成度版本，再逐步扩到社交与跨端同步
1. 对原文档的审核结论
原稿的优点很明显：目录结构清晰，已经覆盖了“产品需求、UI、技术实现、测试验证”四大章节，说明作者已经从概念阶段进入到执行阶段，而不是停留在想法层。
但它仍然不能算“完整开发文档”，原因不是写得少，而是少了决定成败的几个底层部分。下面先给出明确判断。
1.1 原稿已经做对的部分
• 已经给出了融合方向：以 HabitDone 的轻量习惯追踪为底，再叠加 OffScreen 的数字健康、番茄ToDo 的强专注、DayMark 的层级拆解。
• 已经给出了视觉风格方向：偏 HabitDone 的简洁结构，辅以 OffScreen 的高级留白和克制图表。
• 已经写了相当细的功能项、测试项和交互原则，说明需求密度足够高。
• 已经在尝试用 Flutter 做双端统一，这是低成本方案里最现实的方向之一。
1.2 原稿缺失或需要修正的核心点
• 缺少“四个 APP 分别分析”这一层。用户最初的要求是先把四款 APP 各自做什么、有什么功能、有什么特色拆清楚，再做融合；原稿直接跳到融合版，少了“来源依据”。
• 缺少版本优先级。所有功能一次性全做，会直接把复杂度拉满；真正落地必须拆成 MVP、V1、V2，否则开发与测试成本会失控。
• 缺少统一数据模型。一个四合一产品至少要定义 Goal / Task / Habit / Focus Session / Screen Rule / Report / Reward 等基础对象，否则后面会越做越乱。
• 缺少完整信息架构。现在只有主页面描述，没有首开引导、权限流程、空白状态、失败状态、阻断状态、详情页、编辑页、报告页这些关键页面。
• 技术表述过于绝对。尤其是 iOS 的屏幕时间、应用阻断、TestFlight、远程推送、云同步额度这些地方，不能直接按“免费、简单、100%可用”处理。
2. 四个原型 APP 的逐个拆解
这一章补的是原稿最关键的缺口：把四个原型 APP 各自的定位、功能、特色、能带到新产品里的价值讲清楚。
2.1 DayMark：你需要继承它的“层级思维”
• 定位：不是单纯的习惯打卡，而是“一个项目下可继续拆子项目”的追踪工具。
• 强项：把复杂目标拆成更细的执行项，很适合学习计划、健身计划、工作项目、周期性主题追踪。
• 可继承功能：目标树、项目树、父子级进度汇总、按主题组织记录、同一目标下的多项行动联动。
• 在新 APP 里的角色：负责“规划层”和“结构层”，解决用户长期目标无法落地的问题。
2.2 OffScreen：你需要继承它的“数字健康 + 高级感”
• 定位：不仅是屏幕时间统计，更是数字健康管理工具。
• 强项：能把“手机拿起次数、边走边看、起床后多久拿手机、睡前多久放下手机”这些行为变成可读数据。
• 可继承功能：总屏幕时长、拿起次数、分应用统计、禁用时段、专注模式、白名单、睡眠联动、可视化报告。
• 在新 APP 里的角色：负责“数字行为反馈”和“克制高级的图表表达”，让产品不只是任务工具，而是自我管理工具。
2.3 番茄ToDo：你需要继承它的“强执行引擎”
• 定位：本质是番茄钟 + 待办 + 强约束专注系统。
• 强项：不只是计时，而是通过学霸模式、强提醒、白噪音、打断记录等机制把用户拉回执行状态。
• 可继承功能：番茄钟、正倒计时、严格模式、翻转专注、白噪音、专注历史、待办绑定、学习统计、自习室。
• 在新 APP 里的角色：负责“行动层”和“执行层”，让目标不只是写下来，而是真正被做掉。
2.4 HabitDone：你需要继承它的“轻量首页与主题系统”
• 定位：现代、简约、输入成本低的习惯追踪工具。
• 强项：页面非常轻，颜色柔和，热力图和多次打卡很好用，用户几乎不用学习成本。
• 可继承功能：多习惯管理、每日多次打卡、热力图、提醒、图标与描述、主题色自定义。
• 在新 APP 里的角色：负责“日常高频入口”，让产品即便融合很多能力，也不会一打开就显得重。
3. 四合一之后，这个 APP 最终应该有什么功能
融合不是简单相加，而是要把四个来源能力重组为一个统一系统。下面这份功能结构，既保留四款原型 APP 的优势，又避免用户打开后像进入四个独立产品。
3.1 最终产品定位（一句话版）
3.2 统一数据模型（非常重要）
• Goal：长期目标，例如考研、减脂、英语提升、个人项目。
• Project / Subproject：目标下的项目与子项目，对应 DayMark 的层级拆解能力。
• Task：一次性待办或阶段性执行项。
• Habit：高频重复行为，例如早睡、阅读、背单词、喝水。
• Focus Session：每次专注记录，包括时长、模式、绑定对象、是否中断。
• Screen Rule：屏幕与应用限制规则，例如某应用每日限额、睡前禁用、专注时屏蔽。
• Report：日 / 周 / 月 / 年复盘快照。
• Reward / Achievement：奖励与成就系统。
3.3 大功能一：目标规划与项目拆解系统
• 支持总目标、主项目、子项目、执行项四级起步，允许继续向下扩展。
• 每个节点都能设置截止时间、优先级、标签、里程碑、完成规则。
• 支持父子节点进度自动汇总，让用户知道“整体推进到哪里了”。
• 支持把目标节点绑定到具体习惯、待办、专注时段，形成真正的闭环。
3.4 大功能二：今日执行中心
• 首页优先展示“今天要做什么”，而不是一上来先展示全部历史数据。
• 统一容纳今日待办、今日习惯、今日目标节点、今日专注计划、今日屏幕目标。
• 支持智能排序：先显示快到期、高优先级、连续打卡即将中断、今日尚未开始的项目。
• 支持一键快速开始专注、快速打卡、快速新建。
3.5 大功能三：习惯养成与打卡系统
• 支持正向习惯和反向习惯，例如“阅读 30 分钟”和“少刷短视频”。
• 支持每天多次打卡、目标数值打卡、补卡、跳过、备注、图片记录。
• 支持连续打卡 streak、streak 保护、里程碑提醒、暂停与归档。
• 支持习惯与目标联动：某习惯完成后，自动给对应目标累计进度。
3.6 大功能四：专注执行系统
• 完整支持番茄钟、倒计时、正计时、累计专注四种模式。
• 支持严格模式、学霸模式、翻转专注、白名单、打断记录、提前退出惩罚。
• 支持白噪音、专注标签、绑定待办/习惯/目标、专注完成后的即时复盘。
• 支持从首页直接发起专注，降低进入成本。
3.7 大功能五：数字健康与戒断系统
• 统计总屏幕时长、应用使用排行、拿起次数、平均单次查看时长、早晚使用习惯等。
• 支持总时长限额、单应用限额、特定时段禁用、睡前无手机规则。
• 支持“无手机挑战”“碎片化使用戒断挑战”以及与专注模式联动。
• 把数字健康做成“行为反馈系统”，而不是单独一个冷冰冰统计页。
3.8 大功能六：数据可视化与成长复盘系统
• 习惯侧用热力图和完成率排行呈现。
• 目标侧用树状进度与阶段达成率呈现。
• 专注侧用趋势图、时段分布、模式分布呈现。
• 数字健康侧用时间轴、排行和关联分析呈现。
• 系统自动生成日 / 周 / 月复盘，并给出“做得好 / 可优化”的提示。
3.9 大功能七：激励与监督系统
• 支持里程碑勋章、成长等级、连续完成奖励、用户自定义奖励。
• 支持轻社交监督，例如自习室、打卡小队、只读型排行榜。
• 默认以个人使用为主，社交能力做成可开可关，避免产品变杂。
3.10 大功能八：个性化与隐私系统
• 支持全局主题色、深浅模式、字号、圆角、图标风格、信息密度自定义。
• 支持单个习惯、单个目标卡片独立设色。
• 支持应用锁、面容/指纹、数据导出、本地备份、可选云同步。
• 遵循“本地优先、云端可选、不给用户制造强制登录焦虑”。

4. 打开 APP 后，内容应该如何布局：推荐 UI 架构
原稿已经写了视觉规范，但“页面怎么串起来”还不够完整。这一章补的是信息架构，也就是用户打开 APP 以后，从第一屏到关键功能页到底怎么走。
4.1 视觉风格总原则
• 结构上向 HabitDone 学：轻、快、低学习成本、列表优先。
• 质感上向 OffScreen 学：大留白、重点数据放大、图表克制、阴影极轻。
• 颜色上走低饱和路线：默认高级耐看，同时允许用户自己换主题色。
• 操作上坚持“高频动作 1 步触达，低频动作 2～3 步触达”。
4.2 推荐信息架构：不是只有 4 个主页面，还要有关键二级页面
4.3 关键二级页面清单（原稿缺少）
• 首开引导页：介绍产品价值，不要超过 3 屏。
• 权限引导页：把通知、使用情况访问、专注相关权限拆开说明，不要一次性全要。
• 快速新建抽屉：统一添加目标 / 任务 / 习惯 / 专注计划。
• 目标树详情页：查看某个目标下面的全部子结构。
• 编辑页：任何对象都尽量用底部抽屉或半屏弹层编辑。
• 数字健康详情页：查看具体应用排行、时间轴和限制规则。
• 复盘详情页：查看完整日报、周报、月报。
• 空状态页 / 权限拒绝页 / 屏蔽生效页 / 导出完成页：这些状态页必须补齐。
4.4 首次打开 APP 的页面流程
• Splash：只停留极短时间，用于载入主题与本地数据。
• 欢迎页：一句话告诉用户这是“目标 + 习惯 + 专注 + 戒手机”的一体化工具。
• 偏好选择：让用户勾选更偏向“习惯养成 / 学习专注 / 数字戒断 / 综合规划”，决定首页默认模块排序。
• 权限引导：先要通知权限；使用情况访问、应用限制等高敏权限延后到真正使用该功能时再申请。
• 进入首页：看到今日卡片，而不是先看到复杂设置。
4.5 今日页布局（建议作为默认首页）
• 顶部：日期、问候语、右上角全局“+”与筛选按钮。
• 第一屏：今日完成率、今日专注时长、今日屏幕目标、连续打卡天数四个轻量数据块。
• 第二屏：今日待办列表，支持勾选、拖拽排序、滑动编辑。
• 第三屏：今日习惯列表，支持快速打卡、长按补卡、展开查看说明。
• 第四屏：今日重点目标卡，告诉用户此刻最重要的 1～3 个推进项。
• 悬浮动作：底部固定“开始专注”按钮，减少跳转。
4.6 计划页布局
• 上方分段控件：目标 / 任务 / 习惯 三个视图切换。
• 目标视图：树状层级 + 进度条 + 里程碑标记。
• 任务视图：支持按日期、优先级、标签筛选。
• 习惯视图：支持查看全部习惯、归档习惯、暂停习惯。
• 这个页面承担“整理结构”的作用，所以要比首页稍微更信息化，但仍保持清晰留白。
4.7 专注页布局
• 核心区域放一个巨大的计时器，视觉中心必须足够强。
• 计时器下方显示本次绑定对象：哪个任务、哪个目标、哪个习惯。
• 模式切换区放在计时器下方：番茄 / 倒计时 / 正计时 / 累计。
• 再下方是规则区：白名单、翻转专注、严格模式、白噪音。
• 页面底部提供“查看数字健康规则”，承接 OffScreen 能力。
4.8 复盘页布局
• 顶部时间粒度切换：日 / 周 / 月 / 年。
• 第一模块：总览卡，展示核心 4 指标。
• 第二模块：习惯热力图与连续天数。
• 第三模块：目标树进度与阶段完成率。
• 第四模块：专注趋势、专注时段、模式占比。
• 第五模块：屏幕行为统计与应用排行。
• 最后一个模块放 AI 风格总结语，但不要喧宾夺主。
4.9 我的页布局
• 第一组优先放主题与外观，因为这正是用户强感知的特色功能。
• 第二组放提醒、隐私、安全、权限中心。
• 第三组放备份与同步、导入导出。
• 第四组放帮助、反馈、关于、版本说明。
• 保持纯列表，不做过多卡片，让设置页简洁干净。
4.10 状态设计：这决定 UI 是否真正能承载全部功能
• 空状态：新用户第一次打开时，不能是空白页面，要给出示例卡片与引导操作。
• 加载状态：统计页和报告页必须有骨架屏或渐进加载。
• 权限拒绝状态：要明确告诉用户为什么需要权限、现在还能用什么、去哪里打开。
• 专注阻断状态：当严格模式生效时，页面文案必须明确，不然用户会以为卡死。
• 同步冲突状态：如果未来加入云同步，必须设计“本地覆盖云端 / 云端覆盖本地 / 手动合并”。

5.1 建议采用的基准设计尺寸
5.2 推荐设计 token
• 间距：4 / 8 / 12 / 16 / 24 / 32。
• 圆角：小元素 8，中等卡片 16，重点面板 20。
• 标题：24～28；正文：14～16；辅助：12～13；计时器大字：48～60。
• 点击热区：最小 44×44，实际优先按 48×48 设计更稳。
• 列表密度：默认中密度；在设置中允许切换“紧凑 / 标准 / 舒展”。
5.3 这套 UI 能否承载全部功能？
• 真正决定功能会不会被 UI 埋掉的，不是页面好不好看，而是信息架构有没有分层。
• 你不应该把所有功能都塞进首页；应该把首页做成“高频操作中心”，把结构化编辑和深度分析放到二级页。
• 所以答案不是“原稿 UI 完全不行”，而是“原稿 UI 只够描述主框架，不够直接开发”。
6. 技术落地：如何把成本降到最低，同时不把自己骗进去
这部分是对原稿技术章的修正版。方向上仍然推荐 Flutter，但必须把“能免费开发”和“能免费公开分发”分开说，把“能做”和“能 100% 无差异做好”分开说。
6.1 推荐技术路线
• 客户端：Flutter 作为主框架，负责绝大多数页面与状态流。
• 本地数据库：优先 SQLite / Drift 一类更适合结构化数据的方案；如果只做轻量本地数据，也可以选择其他本地库。
• 状态管理：选一个主流、可维护、AI 也容易生成代码的方案，不要混用多个模式。
• 原生扩展：Android 的使用情况与拦截能力、iOS 的 Screen Time / Family Controls / Device Activity，建议保留原生层实现能力，不要幻想纯 Flutter 插件一把梭。
6.2 最省钱的开发顺序
• 第一阶段：先做本地单机版，不要一开始就上云同步、社交、自习室。
• 第二阶段：先让 Habit / Task / Focus 跑通，再加入 Goal Tree。
• 第三阶段：再做数字健康统计；最后才做强应用限制与社交。
• 这样能最大化降低你在权限、平台差异、后端、审核上的风险。
6.3 iOS 与 Android 的关键差异（必须写进开发文档）
6.4 推送与提醒：本地通知和远程推送要分开写
• 本地通知：完全可以优先做，并且对习惯提醒、截止提醒、专注完成提醒已经足够有价值。
• 远程推送：只有当你做云同步、多人监督、自习室、跨设备消息时，才真的必须上。
• 产品早期如果以“个人单机效率工具”为主，本地通知优先级远高于远程推送。
• 这能显著降低后端、账号、证书与送达链路复杂度。
6.5 数据存储的现实方案
• MVP：本地优先存储，绝大多数数据保存在用户设备上。
• 需要多设备同步时：先同步文本型和结构化数据，不要急着同步图片、附件、海量报告。
• 如果未来加云端，建议先做“手动备份 / 恢复”，再做“实时同步”。
• 同步冲突处理要提前设计，否则用户会非常容易丢数据。
6.6 成本边界（务必写清）
7. 测试与验收：如何保证双平台稳定
原稿的测试意识是对的，但还需要把测试对象和风险点再拉实一点。
• 功能测试：高频主链路优先，先测创建、打卡、专注开始/结束、目标进度联动、提醒触发。
• 权限测试：分别测试通知、使用情况访问、数字健康、应用限制等权限在允许 / 拒绝 / 中途关闭时的表现。
• 兼容性测试：安卓厂商系统、不同 iPhone 尺寸、平板布局、深浅模式、字体放大都要单独过一遍。
• 性能测试：长时间专注计时、重度图表渲染、海量本地数据、后台恢复是重点。
• 合规测试：隐私政策、权限说明、数据导出与删除、第三方 SDK 清单必须提前准备。
7.1 推荐验收标准
• 首页主要交互 1 秒内可响应，关键页面无明显卡顿。
• 习惯、任务、专注、目标、统计五条主链路全可闭环。
• 权限拒绝时不会让 APP 直接不可用，而是给出降级方案。
• 深浅色切换、主题切换、字体缩放后不出现布局崩坏。
• 本地数据在异常退出后不丢失。
